# Архітектура вебзастосунків і REST API

Конспект основних понять за презентацією **«05 Web_Apps_Architecture_RestAPI.pdf»**. Номери сторінок нижче відповідають PDF. Типові запитання сформульовано для повторення матеріалу; це не готовий перелік запитань із презентації. Приклади HTTP-відповідей, пояснення CORS і практичні уточнення доповнюють матеріал слайдів.

## 1. Клієнт-серверна модель

*Основа: стор. 3–4.*

**Клієнт** надсилає запит, **сервер** приймає його, виконує потрібну роботу й повертає відповідь. Клієнтом може бути браузер, мобільний застосунок, Postman або `curl`.

Клієнт і сервер — ролі програм. Flask є сервером для React, але під час звернення до окремого сервера БД сам виступає клієнтом.

```text
Клієнт                 Backend                 База даних
   | -- HTTP-запит ------> |                        |
   |                      | -- запит до БД ------> |
   |                      | <----- результат ----- |
   | <---- відповідь ---- |                        |
```

Одна вебсторінка зазвичай спричиняє багато запитів: окремо за HTML, CSS, JavaScript, зображеннями та даними API. Частина ресурсів може надходити з інших серверів.

## 2. HTTP: запит і відповідь

*Основа: стор. 4–7; структуру повідомлень і коди статусів додано для практики.*

**HTTP — Hypertext Transfer Protocol**, протокол обміну повідомленнями між клієнтом і сервером. **HTTPS** захищає цей обмін за допомогою TLS.

Запит містить метод, адресу ресурсу, заголовки та, за потреби, тіло:

```http
POST /api/products HTTP/1.1
Host: localhost:5000
Content-Type: application/json
Accept: application/json

{"name":"Tea","price":45}
```

Відповідь містить код статусу, заголовки та, за потреби, тіло:

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"message":"Product added successfully.","productId":6}
```

`productId: 6` тут умовний: фактичний ідентифікатор залежить від вмісту БД.

| Частина | Що означає |
|---|---|
| Метод | Яку дію просить виконати клієнт: `GET`, `POST` тощо |
| URL | Адреса ресурсу, наприклад `http://localhost:5000/api/products/1` |
| Headers | Метадані повідомлення: формат, авторизація, правила кешування |
| Body | Дані повідомлення, наприклад JSON нового товару |
| Status code | Результат обробки запиту |

### Коди статусів, які варто знати

| Код | Значення | Типовий випадок |
|---|---|---|
| `200 OK` | Запит успішний | Отримали товар або результат оновлення |
| `201 Created` | Ресурс створено | Додали товар |
| `204 No Content` | Успіх без тіла відповіді | API видалило ресурс і не повертає дані |
| `400 Bad Request` | Некоректний запит | Відсутнє обов'язкове поле або неправильний тип |
| `401 Unauthorized` | Потрібна дійсна автентифікація | Немає токена або він недійсний |
| `403 Forbidden` | Доступ заборонено | Недостатньо прав для операції |
| `404 Not Found` | Ресурс не знайдено | Товар із таким ID відсутній |
| `405 Method Not Allowed` | Метод не підтримується для цієї адреси | `PUT` для маршруту, який має лише `GET` і `PATCH` |
| `500 Internal Server Error` | Внутрішня помилка сервера | Необроблений виняток у backend |

Класи кодів: `2xx` — успіх, `3xx` — перенаправлення та пов'язані механізми кешування, `4xx` — проблема із запитом або доступом, `5xx` — помилка на стороні сервера.

## 3. Як передаються параметри

*Основа: стор. 6–7, 26–29.*

| Спосіб | Приклад | Призначення |
|---|---|---|
| Path parameter | `/api/products/1` | Вибір конкретного ресурсу |
| Query parameter | `/api/products?limit=10&sort=price` | Фільтрація, сортування, пагінація |
| Header | `Authorization: Bearer <token>` | Авторизація та інші метадані |
| Body | `{"name":"Tea","price":45}` | Дані для створення або оновлення |

У query string перший параметр починається після `?`, наступні розділяються `&`. Спеціальні символи у значеннях потрібно кодувати.

Тіло може містити JSON, XML, форму `application/x-www-form-urlencoded`, файл через `multipart/form-data` або інші дані. Твердження зі слайда, що дані **завжди** передаються як словник, є спрощенням прикладу HTML-форми.

Приклад `?limit=10&sort=price` показує загальну ідею: у поточному Flask API ці параметри не реалізовані.

## 4. Дворівнева, трирівнева та N-tier архітектура

*Основа: стор. 8–12.*

**Tier** — рівень розгортання системи. **Layer** зазвичай означає логічний шар коду, наприклад бізнес-логіку. Кілька логічних шарів можуть працювати в одному процесі.

| Модель | Спрощена схема | Ідея |
|---|---|---|
| 2-tier у презентації | Браузер → вебсервер | Два основні рівні взаємодії |
| 3-tier | Браузер → сервер застосунку → сервер БД | Інтерфейс, логіка та зберігання даних розділені |
| N-tier | Клієнт → додаткові рівні → застосунок → дані | Архітектуру розширюють відповідно до потреб |

У розгорнутій системі можуть бути балансувальник навантаження, кілька серверів застосунку, кеш, черга повідомлень і сервер БД. **Балансувальник** розподіляє запити між екземплярами застосунку. Кілька однакових екземплярів збільшують потужність рівня, але самі по собі не утворюють нові рівні.

У цьому навчальному проєкті React, Flask і SQLite виконують три логічні ролі. SQLite працює як вбудована БД із файлом, тому окремого сервера БД тут немає.

## 5. Frontend, backend і класичний вебзастосунок

*Основа: стор. 11, 13–18.*

| Частина | Де виконується в цьому проєкті | За що відповідає |
|---|---|---|
| **Frontend** | React у браузері | Інтерфейс, події користувача, запити до API, відображення результатів |
| **Backend** | Python/Flask на сервері | Обробка запитів, перевірка даних, бізнес-логіка, робота з БД |
| **База даних** | SQLite через backend | Зберігання товарів |

**Бізнес-логіка** — правила предметної області: наприклад, які поля потрібні для товару та хто може змінювати його ціну. **Шар доступу до даних** виконує операції з БД.

У **класичному вебзастосунку** сервер формує HTML і надсилає готову сторінку браузеру. У застосунку з окремим frontend сервер API часто повертає дані, а інтерфейс оновлює JavaScript у браузері. Ці підходи можна поєднувати.

Перевірка у браузері покращує зручність, але backend теж має перевіряти дані: запит можна надіслати напряму через `curl`, оминаючи форму.

## 6. AJAX

*Основа: стор. 15–18.*

**AJAX — Asynchronous JavaScript and XML**. Це підхід, за якого JavaScript надсилає запит і оновлює частину сторінки без її повного перезавантаження.

Попри назву, XML не обов'язковий: часто використовують JSON. Запити можна виконувати через `fetch` або інші HTTP-клієнти.

```javascript
async function loadProducts() {
  const response = await fetch('http://localhost:5000/api/products');
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  return response.json();
}
```

Поки очікується відповідь, браузер може обробляти інші події. `await` призупиняє виконання відповідної асинхронної функції до отримання результату.

## 7. JSON і XML

*Основа: стор. 19–20.*

**JSON — JavaScript Object Notation**, текстовий формат даних. Підтримує об'єкти, масиви, рядки, числа, булеві значення та `null`. Використовується багатьма мовами, зокрема Python.

```json
{
  "id": 1,
  "name": "Tea",
  "price": 45,
  "available": true,
  "tags": ["drink", "hot"],
  "description": null
}
```

Ключі та рядки записують у подвійних лапках; стандартний JSON не підтримує коментарі й зайву кому після останнього елемента.

**XML — eXtensible Markup Language**, текстовий формат із тегами й атрибутами:

```xml
<product id="1">
  <name>Tea</name>
  <price>45</price>
</product>
```

Обидва формати описують дані. JSON часто компактніший і зручний для вебклієнтів; XML корисний у системах, які використовують його структуру та інструменти.

## 8. API та REST API

*Основа: стор. 21–28; принципи REST деталізовано для пояснення.*

**API — Application Programming Interface**, узгоджений спосіб взаємодії програм. Він визначає доступні операції, вхідні дані та результати. API може бути інтерфейсом бібліотеки, операційної системи або мережевого сервісу.

**REST — Representational State Transfer**, архітектурний стиль. **REST API** організовує взаємодію навколо ресурсів та їхніх представлень.

- **Ресурс:** сутність, наприклад товар або замовлення.
- **URI/URL ресурсу:** його ідентифікатор або адреса, наприклад `/api/products/1`.
- **Представлення:** дані ресурсу, передані клієнту, наприклад JSON товару.
- **Endpoint:** точка доступу до API. Конкретну операцію зручно описувати парою методу та шляху: `GET /api/products/1`.

Приклад із презентації: `/book/3/page/35` позначає сторінку 35 книги 3. URL ідентифікує ресурс API, але не зобов'язаний буквально повторювати первинний ключ або структуру таблиць БД.

### Основні обмеження REST

| Принцип | Просте пояснення |
|---|---|
| Client–server | Клієнтський інтерфейс і серверна обробка мають окремі ролі |
| Stateless | Кожен запит містить достатньо контексту для обробки; сервер не покладається на збережений контекст попередньої клієнтської розмови |
| Cacheable | Відповіді визначають можливість і правила кешування |
| Uniform interface | Єдиний підхід до ідентифікації ресурсів, представлень і повідомлень; повний REST також передбачає посилання для доступних переходів |
| Layered system | Між клієнтом і сервером можуть працювати проміжні рівні, наприклад проксі |
| Code on demand — необов'язковий | Сервер може передати клієнту код для виконання |

**Stateless не означає відсутність БД.** Товари зберігаються на сервері, але контекст доступу, наприклад токен, клієнт передає в кожному потрібному запиті. Самого JSON і набору CRUD-маршрутів недостатньо для відповідності всім обмеженням REST.

## 9. CRUD і методи HTTP

*Основа: стор. 5, 25–28.*

**CRUD — Create, Read, Update, Delete:** створення, читання, оновлення та видалення даних.

| Метод | Типове призначення | Приклад | CRUD |
|---|---|---|---|
| `GET` | Отримати ресурс або колекцію | `GET /api/products/1` | Read |
| `POST` | Створити ресурс у колекції або виконати обробку | `POST /api/products` | Зазвичай Create |
| `PUT` | Створити або повністю замінити представлення за заданою адресою | `PUT /api/products/1` | Create / Update |
| `PATCH` | Частково змінити ресурс | `PATCH /api/products/1` | Update |
| `DELETE` | Видалити ресурс | `DELETE /api/products/1` | Delete |
| `HEAD` | Отримати метадані, які надав би `GET`, без тіла | `HEAD /api/products` | — |
| `OPTIONS` | Отримати відомості про можливості взаємодії | `OPTIONS /api/products` | — |

На слайді також є `TRACE` для діагностики та `CONNECT` для встановлення тунелю через проксі. Для звичайних CRUD-операцій вони не потрібні.

**Safe, або безпечний метод**, за своєю семантикою не просить змінити стан ресурсу. Приклади: `GET`, `HEAD`, `OPTIONS`. Це не означає шифрування чи відсутність службових записів у логах.

**Ідемпотентність** означає, що повторення однакового запиту має той самий задуманий ефект на стан сервера, що й один запит. `GET`, `PUT` і `DELETE` ідемпотентні за семантикою; `POST` загалом ні. `PATCH` може бути ідемпотентним залежно від операції: «встановити ціну 50» і «збільшити ціну на 5» поводяться по-різному.

Другий `DELETE` може повернути `404` замість початкового `200`, але ресурс усе одно залишається видаленим. Ідемпотентність не вимагає однакової відповіді.

`GET` слід використовувати для читання. Навіть якщо програмно можна реалізувати видалення через `GET`, це порушує його семантику та може спричинити небажані зміни через кешування або автоматичне завантаження посилань.

## 10. Cookies, автентифікація та авторизація

*Основа: згадка cookies на стор. 39 і приклади входу та Bearer-токена на стор. 29; пояснення доповнено.*

**Cookie** — невелике значення, яке браузер зберігає й надсилає з відповідними запитами за правилами домену, шляху та інших атрибутів. Cookie може містити ідентифікатор сесії або налаштування користувача.

**Автентифікація** відповідає на запитання «хто ви?», а **авторизація** — «що вам дозволено?». Один зі способів передати облікові дані — заголовок:

```http
Authorization: Bearer <access_token>
```

Наявність cookie сама по собі не визначає відповідність REST: важливо, чи потрібен серверу збережений контекст клієнтської сесії. У прикладі Flask із цієї папки автентифікацію не реалізовано.

## 11. Моноліт і мікросервіси

*Основа: стор. 30–31.*

| Критерій | Моноліт | Мікросервіси |
|---|---|---|
| Структура | Основні модулі є одним застосунком | Систему поділено на окремі сервіси за відповідальністю |
| Розгортання | Зазвичай один спільний артефакт | Сервіси можна розгортати незалежно |
| Взаємодія | Часто виклики всередині процесу | Мережеві API або повідомлення |
| Масштабування | Можна запускати кілька копій усього застосунку | Можна окремо масштабувати потрібний сервіс |
| Складність експлуатації | Зазвичай простіше почати | Потрібно керувати мережевими збоями, сумісністю й спостережуваністю |

Приклад мікросервісів із презентації: користувачі, каталог, кошик, замовлення, платежі та доставка. Черга повідомлень дозволяє передавати роботу асинхронно.

**Моноліт може мати кілька логічних шарів і окрему БД.** Він не обов'язково є однорівневою системою. Поділ на tiers і поділ на сервіси описують різні властивості архітектури. React + один Flask backend самі по собі не утворюють мікросервісну систему.

## 12. Конфігурація та `.env`

*Основа: стор. 32–35.*

**Конфігурація** задає параметри роботи програми: порт, адресу API, підключення до БД, рівень логування. Її відокремлюють від коду, щоб змінювати налаштування для різних середовищ.

Поширені формати: `.properties`, XML, JSON, YAML, INI. **Змінні середовища** — ще один спосіб передати налаштування процесу.

**`.env`** — текстовий файл зі значеннями, наприклад:

```dotenv
REACT_APP_BASE_URL=http://localhost:5000/api
```

Ця змінна використовується frontend у цьому проєкті. Шлях `/products` додається до базової адреси, утворюючи `http://localhost:5000/api/products`. У поточному `react/.env.example` адреса наведена без `/api`; для маршрутів цього Flask backend у власному `.env` потрібне значення з прикладу вище.

Файл `.env` має завантажувати відповідний інструмент або бібліотека. Python `os.environ` і Node.js `process.env` дають доступ до середовища процесу, але саме звернення до них не читає довільний файл `.env`.

Секрети не слід комітити; для прикладу налаштувань використовують `.env.example` без секретних значень. Змінні, включені у frontend-збірку, доступні користувачу: пароль БД або приватний API-ключ туди поміщати не можна.

## 13. Перевірка API: curl, Postman, Swagger

*Основа: стор. 29, 36–38.*

| Інструмент | Для чого потрібен |
|---|---|
| **curl** | HTTP-запити з термінала, швидка перевірка та скрипти |
| **Postman** | Графічне створення запитів, колекції, змінні середовища та перевірки відповідей |
| **OpenAPI / Swagger UI** | OpenAPI описує контракт API; Swagger UI показує інтерактивну документацію і дозволяє виконувати запити |
| **Автоматизовані тести** | Перевірка статусів, даних і сценаріїв без ручного повторення |

Selenium, згаданий на слайді, переважно автоматизує браузер і підходить для перевірки всього користувацького сценарію. Окремі API-запити зазвичай простіше перевіряти HTTP-клієнтом.

Swagger UI не створює реалізацію backend і потребує опису API. Під час перевірки дивляться не лише на `200`, а й на тіло, заголовки, збережені зміни та помилки: відсутній товар, пропущені поля, неправильні типи.

### Приклади для цього проєкту

Передумова: backend запущено на `http://localhost:5000` за інструкцією з [README](README.md). Команди створення, оновлення та видалення змінюють локальні дані.

```bash
# Список товарів. Без явного методу curl використовує GET.
curl -i http://localhost:5000/api/products

# Створення товару.
curl -i -X POST http://localhost:5000/api/products \
  -H 'Content-Type: application/json' \
  -d '{"name":"Tea","price":45}'

# Підставте productId із відповіді попередньої команди.
PRODUCT_ID=6

# Отримання створеного товару.
curl -i "http://localhost:5000/api/products/$PRODUCT_ID"

# Часткове оновлення.
curl -i -X PATCH "http://localhost:5000/api/products/$PRODUCT_ID" \
  -H 'Content-Type: application/json' \
  -d '{"price":50}'

# Видалення.
curl -i -X DELETE "http://localhost:5000/api/products/$PRODUCT_ID"
```

Параметри `curl`: `-i` показує також заголовки відповіді, `-X` задає метод, `-H` додає заголовок, `-d` передає тіло. У цьому Flask API створення повертає `201`, успішні `PATCH` і `DELETE` — `200`, звернення до відсутнього товару — `404`. Метод `PUT` для товару не реалізовано.

## 14. Як усе пов'язано у `devops_task_api`

```text
Браузер із React                     Flask                 SQLite
http://localhost:3000        http://localhost:5000         products.db
         |                           |                       |
         | -- GET /api/products ---> | -- читання товарів --> |
         |                           | <------ дані -------- |
         | <------ JSON + 200 ------ |                       |
         |                           |                       |
         +-- оновлює список товарів без перезавантаження -----+
```

Це схема запущеного локально навчального застосунку. Порти `3000` і `5000` належать різним процесам, які можуть працювати на одному комп'ютері.

**CORS — Cross-Origin Resource Sharing** — механізм, за яким сервер через HTTP-заголовки дозволяє браузеру читати відповіді з іншого origin. Origin визначається схемою, хостом і портом, тому `http://localhost:3000` та `http://localhost:5000` мають різні origin.

У [Flask backend](python-backend/app.py) CORS налаштовано для `/api/*`. Для деяких запитів браузер спочатку надсилає `OPTIONS` — preflight-перевірку. `curl` не застосовує браузерні правила CORS, тому успішний запит у терміналі ще не гарантує успішного читання відповіді у frontend. CORS не замінює автентифікацію.

## 15. Типові запитання та короткі відповіді

### 1. Що відбувається, коли користувач відкриває вебсторінку?

Браузер отримує HTML, завантажує потрібні CSS, JavaScript та інші ресурси. JavaScript може додатково звертатися до API, а backend — до БД. Результат відображається користувачу.

### 2. Чим frontend відрізняється від backend?

Frontend відповідає за інтерфейс і взаємодію з користувачем, backend — за серверну обробку, бізнес-правила та доступ до даних. У цьому проєкті це React і Flask відповідно.

### 3. Чим вебсервер відрізняється від сервера застосунку?

Вебсервер приймає HTTP-запити, може віддавати статичні файли й передавати інші запити далі. Сервер застосунку виконує код програми. Ці ролі можуть бути об'єднані або розділені між процесами.

### 4. Що означає 3-tier і чи потрібні три комп'ютери?

Це поділ на представлення, обробку та дані з відповідними рівнями розгортання. Для навчання компоненти можуть працювати на одному комп'ютері; кількість фізичних машин не дорівнює кількості логічних ролей.

### 5. Чим класичний вебзастосунок відрізняється від frontend з API?

У класичному варіанті сервер формує HTML. В окремому frontend JavaScript отримує дані з API та оновлює інтерфейс. На практиці можливі змішані підходи.

### 6. Чи AJAX обов'язково використовує XML?

Ні. Назва історична, а формат даних може бути JSON, XML, HTML або іншим. Головне — обмін даними без повного перезавантаження сторінки.

### 7. Чим API відрізняється від REST API?

API — загальне поняття інтерфейсу взаємодії програм. REST API — API, спроєктоване відповідно до архітектурного стилю REST.

### 8. REST — це протокол? А JSON — це REST?

REST — архітектурний стиль, HTTP — протокол, JSON — формат даних. Використання HTTP і JSON саме по собі не робить API повністю RESTful.

### 9. Що таке ресурс і endpoint?

Ресурс — сутність, наприклад товар. Endpoint — точка доступу до API. `GET /api/products/1` отримує представлення товару, а `DELETE /api/products/1` виконує іншу операцію за тією самою адресою.

### 10. Чим GET відрізняється від POST?

`GET` призначений для читання, `POST` — для обробки переданих даних, часто зі створенням ресурсу. Це різниця семантики; захист передавання даних забезпечує HTTPS, а не вибір `POST`.

### 11. Чим PUT відрізняється від PATCH?

`PUT` задає повне бажане представлення ресурсу, `PATCH` описує часткову зміну. У навчальному Flask API для оновлення реалізовано `PATCH`.

### 12. Що таке ідемпотентність?

Повторення однакового запиту має той самий задуманий ефект, що й один запит. Повторне встановлення ціни в `50` не змінить результат; повторне створення товару через звичайний `POST` може створити дублікати.

### 13. Чи stateless означає, що сервер нічого не зберігає?

Ні. Сервер може зберігати товари й інші дані в БД. Вимога стосується контексту запитів: для обробки не повинна бути потрібна пам'ять про попередню клієнтську розмову.

### 14. Чим Content-Type відрізняється від Accept?

`Content-Type` описує формат фактично переданого тіла. `Accept` повідомляє, які формати відповіді прийнятні клієнту. Для JSON часто використовують `application/json`.

### 15. Чим 401 відрізняється від 403, а 400 — від 404?

`401` стосується відсутньої або недійсної автентифікації, `403` — заборони доступу. `400` означає некоректний запит, `404` — відсутність потрібного ресурсу.

### 16. Чи відповідь 200 доводить, що API працює правильно?

Ні. Потрібно перевірити вміст відповіді та фактичний результат операції. Наприклад, після оновлення виконати `GET` і переконатися, що ціна змінилася.

### 17. Чим cookies відрізняються від Bearer-токена?

Cookie — механізм зберігання й автоматичного надсилання значень браузером за певними правилами. Bearer-токен — облікове значення, володіння яким дозволяє доступ; його часто передають у `Authorization`. Це різні поняття, і токен також може зберігатися в cookie.

### 18. Чому API працює через curl, але frontend показує помилку CORS?

Браузер перевіряє правила доступу між origin, а `curl` — ні. Перевірте адресу API, origin frontend, заголовки CORS і результат можливого запиту `OPTIONS`.

### 19. Чи мікросервіси завжди кращі за моноліт?

Ні. Вони дозволяють незалежно розгортати й масштабувати частини системи, але ускладнюють взаємодію та експлуатацію. Для невеликого застосунку моноліт часто простіший.

### 20. Навіщо конфігураційні файли та .env?

Щоб задавати параметри середовища без зміни коду. `.env` є одним зі способів зберігати налаштування для завантаження інструментом; він не шифрує значення і не робить frontend-секрети прихованими.

### 21. Чим Postman відрізняється від Swagger UI?

Postman допомагає складати, виконувати й організовувати запити. Swagger UI відображає контракт OpenAPI як інтерактивну документацію з можливістю виклику описаних операцій.

### 22. Чому DELETE повертає 200, хоча в прикладах часто є 204?

Обидва варіанти можливі залежно від контракту API. У цьому проєкті повертається `200` із JSON-повідомленням. Відповідь `204` не повинна містити тіла.

### 23. Як пояснити цей навчальний проєкт на співбесіді?

«React працює у браузері та надсилає HTTP-запити до Flask API. Backend обробляє CRUD-операції над товарами, перевіряє вхідні дані й працює із SQLite. Відповіді повертаються як JSON. API можна перевіряти через curl або Postman, а адресу backend frontend отримує з конфігурації».

## 16. Шпаргалка для повторення

| Поняття | Що запам'ятати |
|---|---|
| HTTP / HTTPS | Протокол обміну / захищений через TLS обмін |
| Frontend / backend | Інтерфейс / серверна обробка |
| AJAX | Оновлення даних сторінки без повного перезавантаження |

| JSON / XML | Формати представлення даних |
| CRUD | Create, Read, Update, Delete |
| GET / POST | Читання / обробка, часто створення |
| PUT / PATCH | Повна заміна / часткова зміна |
| Stateless | Запит не залежить від збереженої клієнтської розмови |
| Моноліт / мікросервіси | Один застосунок / окремо розгортувані сервіси |
| `.env` | Файл налаштувань, який має завантажити відповідний інструмент |
| curl / Postman / Swagger UI | Термінальні запити / графічний клієнт / інтерактивна документація |
